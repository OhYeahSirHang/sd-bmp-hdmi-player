# 案例：一个 SD→DDR3→HDMI 播放器怎么被这套循环修好

> 板卡：xc7a35tfgg484-2（A7 Lite，DDR3 x16）；
> 功能：SD 卡读 1080p BMP 与 320×240 RGB565 视频，DDR3 双缓冲，1080p60 HDMI + OSD 菜单。
> 目的：把 SKILL.md 的 S0→S5 走一遍，看每一阶段实际产出什么。

---

## 案例 1：目标 15 fps，实测 12 fps

### S0 基线

- 现象：OSD 长期显示 12，稳定不波动；复位/换图都不变。
- 版本三元组：RTL 时间 / bit 时间 / 本次 log 时间——**先确认烧的就是当前 RTL**。

### S1 预算

```text
1080p 像素            = 2,073,600
像素产生域            = 50 MHz（写侧） → 41.47 ms
扫描域                = 148.5 MHz      → 13.96 ms（不是瓶颈）
帧数据                = 320×240×2 = 153,600 B = 300 扇区
SPI 25 MHz 有效带宽   ≈ 3.125 MB/s → 49.2 ms
读法                  300 次 CMD17（每次命令+响应+CRC+间隙）
帧率档位              60/N → 60/30/20/15/12 …
```

**自洽性检验**：生成 41.47 ms，读卡 300 次单块必然更长，合计越过 66.67 ms →
落进 `60/5 = 12`。预算与现象吻合，模型可用。

### S2 假设

| # | 假设 | 预测 | 否证 |
|---|---|---|---|
| H1 | VSYNC 分频量化 | 每帧 ∈ (66.67, 83.33] ms | 实测帧间隔落在此区间外 |
| H2 | 逐扇区命令开销占主导 | 改 CMD18 后读时间降 > 30% | 只降 < 10% |
| H3 | 像素生成超预算 | 单独测生成仍 > 66.67 ms | 生成 < 50 ms |

### S3/S4 实验与修复

1. 仿真打印每帧间隔：`66.668 ms` → H1 成立，且刚好贴着 15 fps 边界；
2. 改 CMD18 一次读 300 块 + CMD12 收尾；视频读时钟 **降到 25 MHz**（限速匹配消费速率）；
3. `vid_player` 每帧一次 CMD18，每 4 个 VSYNC 换帧（节流）；
4. 回归：`RESULT swaps=17 fps=15` + `PACING_OK`。

### S5 结果

| 版本 | fps | LUT | WNS |
|---|---:|---:|---:|
| 修复前 | 12 | 9,670 | +0.365 |
| CMD18 + 25MHz + 4-VSYNC | 15 | 9,697 | +0.230 |

> 关键教训：**12 fps 不是"慢了 20%"，而是"刚刚越过一个量化台阶"**。
> 一旦这么看，2 ms 的优化也可能有决定性意义，反之 10% 的平均提升可能毫无作用。

## 案例 2：切换媒体后整块右移

### 现象指纹

- 只有"视频 → 图片"切换后出现；
- 每次偏移量基本一致；
- 复位后第一次切换不偏，第二次才偏 → 与"残留"类问题吻合。

### 三个并存的根因

| # | 根因 | 现象贡献 |
|---|---|---|
| 1 | `frame_sync` 只清 h/v，未 flush 写 FIFO | 视频残留像素把图片顶掉 N 个像素 |
| 2 | `img_trans` 的 `rd_off` 未在切换时清零 | 偏移累计，越切越偏 |
| 3 | 顶层用原始 `vid_next` 触发 `frame_sync`，而播放器读帧时忽略该键 | 当前帧被中途清行列计数 |

### 为什么"修一处没效果"

只修 #1 时现象"减轻但仍在"，因为 #2 还在；只修 #2 时第一次正常、第二次偏移。
这正是 SKILL.md 规则 7（一次一个变量）和"多现象指向单一根因"的价值：
**先找到能同时解释三条现象的根因组合，再一起改，并且分别验证。**

### 修复

1. `ddr3_rx_buffer`：`frame_sync` 后 flush FIFO 31 个 `ui_clk`；
2. `img_trans`：切换时清 `state / rd_off / swap_allow / first_done`；
3. `vid_player` 增加 `vid_next_ack`，只有真正接受才允许 `frame_sync`；
4. 约束：`u_img_trans/media_s1` 的 CDC 入口加 `false_path`。

回归项：新增断言"切换后首行首像素 x == 0"。

## 案例 3：WNS 从 +0.3 掉到 −4.7

### 事实

- 只加了一个跨域同步器（`media_sel`：50 MHz → 148.5 MHz）；
- 第一条违例路径：起点 50 MHz 域寄存器，终点 148.5 MHz 域**同步器第一级**。

### 判定

这不是真违例，是 STA 把"同步器入口"当普通同步路径检查。

```tcl
set_false_path -from [get_cells u_img_trans/media_s1_reg*] \
               -to   [get_cells u_img_trans/media_s2_reg*]
```

### 验证方式

加约束后 `report_timing` 里**这条路径消失**（不是"数字变好"）。
若路径还在，说明约束没生效。

> 反例：对整片寄存器加 `false_path` 或对整模块设异步时钟组，WNS 也会"变好"，
> 但真 bug 被藏起来，上板会偶发几何错位。

## 案例 4：索引表版本只能扫到 2 张图

### 现象

- 无索引版能扫全部图片；
- 加索引表的版本只能找到 2 张。

### 反推（`timing-budget.md` §5）

```text
1080p BMP24 ≈ 6.22 MB/张；catalog 上限 32 MB → 理论 5 张
实测 2 张 → 数量级不符 → 不是"扫描范围小"，是 catalog 上限截断
```

### 修复

`CATALOG_END` 与 `STOP_ADDR` 统一为 100 MB。
上电 catalog 时间约 17 s，与 `100 MB / 6.25 MB/s ≈ 16 s` 吻合 —— **预算自洽**。

## 这套循环在别处也成立吗？

同一套 S0→S5 在本项目的另外几个问题上复用成功：

| 问题 | 用到的阶段 | 关键数 |
|---|---|---|
| 4 行行缓冲撑不住 SD 抖动 | S1 容量预算 | 2.56 KB 只够 80 µs |
| 边缘模式规则点阵 | S2 假设 + 纯色图实验 | 纯色图应全黑，出现点阵即地址问题 |
| OSD 白字发虚 | S2 判定"是量化不是 bug" | (255,255,255)→(248,252,248) 是 RGB565 正常损失 |
| 视频完全不出图 | S0 基线（dump 扇区 0） | 文件被放进 FAT32 分区而非裸写 |

**通用性判据**：只要问题能写成"某个量超过了某个预算"或"某个状态在切换时没被清"，
这套循环就适用——与厂商、板卡、语言都无关。

# 提示词库（可直接复制）

> 这些模板的共同点：**把"猜"变成"算"，把"改"变成"证"**。
> 任何模型都能用，不依赖特定厂商。中英各一版，效果一致。

---

## P1 预算优先的根因分析（最常用）

**何时用**：拿到一个"现象"，但还没定位。

```text
角色：你是资深 FPGA 视频通路工程师。先不要改代码。

现状：<一句话现象，含实测数值，例如 "目标 15fps，OSD 实测 12fps，稳定不波动">
工程：<器件/时钟/关键模块清单，或让我先读的目录>
约束：<不许改原件 / 只能改副本 / 时间预算>

请按顺序做四件事：
1. 列出把现象翻译成数字所需的全部量（帧周期、像素数、像素时钟、每帧字节数、命令开销），
   缺哪个就明确说"缺"，不要假设；
2. 用这些量算出"现象应该长什么样"，并与实测对照，判断模型是否自洽；
3. 给出不超过 4 条可证伪假设，每条写"预测"和"否证条件"，按能解释的现象数量排序；
4. 为第一条假设设计一个成本最低的实验（静态检查 < 单元 TB < 分阶段 TB < ILA），
   写清观测哪个信号、判据是什么。

输出格式：预算表 → 假设表 → 一个实验方案。不要给"可以试试"这类建议。
```

**期望输出**：一张能自己复算的预算表 + 假设排序 + 单个实验。
**坏回答的特征**：直接给修改代码、说"可能是时序问题"、列 10 条并列假设。

## P2 多假设排序（现象复杂时）

```text
现象清单（按时间顺序）：
1. <切换后整块右移>
2. <复位后第一次切换不偏移，第二次才偏移>
3. <偏移量固定为 N 像素>

请找出能同时解释全部三条的**单一**根因；
若找不到，请给出"必须同时成立的两个原因"，并说明为什么三条现象缺一不可地指向它们。
对每个候选根因，指出哪个现象会**推翻**它。
```

**为什么有效**：多现象同时出现时，人类容易接受"多个 bug 叠加"的解释；
强制要求"单一根因"能过滤掉大部分噪声假设。

## P3 日志证据审计（评审别人的 PASS）

```text
下面是一份"已验证"的结论和日志片段。请不要复述结论，只做审计：

<贴结论 + 日志路径/片段>

回答三个问题，每个都要给证据行：
Q1 这份日志是当前源码产生的吗？（看 xelab 的参数覆盖、时间戳）
Q2 判据是精确还是容差？有没有 FAIL 行被 PASS 结论盖住？
Q3 覆盖了什么、**没覆盖什么**？用表格列，必须有"未覆盖"列。

最后给一个可信度等级：高/中/低，并说明缺哪一项才能升级。
```

**注意**：如果 AI 只说"结论看起来合理"，让它重做——这是拒绝审计。

## P4 只读验证委托（保护原件）

```text
任务：验证 <目录> 的功能，但**不许修改该目录下任何文件**。

规则（必须逐条遵守并在结束时自证）：
1. 开始前对该目录做 SHA256 快照，保存为 baseline；
2. 所有实验在副本 <copy 路径> 中进行；
3. 若必须改原件才能跑通，改为：shadow 模块 / 层次化 force / 复制后改路径；
4. 结束时：跑一次快照比对，差异必须为空；列出"副本里改过哪些文件"；
5. 结论里明确区分"原件行为"与"副本行为"。

现在开始：先只做静态审计（不改任何东西），报告 3 个最可能的问题 + 需要的证据。
```

## P5 时序违例解读

```text
WNS = <值>，WHS = <值>，WPWS = <值>；器件 <part>；时钟 <列表>。
第一条违例路径（report_timing -max_paths 1 的原文）：
<贴路径>

请：
1. 判断这条路径是"真违例"还是"跨域同步器入口被当同步路径"；
2. 若是跨域，给出**最小范围**的约束写法（只到同步器入口），并说明加完后应观察到什么变化；
3. 若不是跨域，按"逻辑级数 / 扇出 / 布线拥塞 / 时钟不确定性"四类归因，给出排查顺序；
4. 若 WPWS 为负，先判断违例端点是否集中在 SERDES，再决定是否算已知项。
```

**坏回答**：直接建议对整片寄存器加 `false_path`，或建议降低时钟频率。

## P6 算法上 FPGA 的可行性（软硬件划分）

```text
算法：<描述>；目标：<分辨率/帧率>；器件：<LUT/DSP/BRAM 预算>。

请先算，再判断：
1. 每帧运算量（MAC/像素、访存字节、窗口依赖）；
2. 需要的并行度 = 运算量 / 帧时间预算；
3. 对应资源（DSP、BRAM、LUT）与可达时钟；
4. 若放不下，给出三条降级路径（降分辨率/降帧率/换近似算法）及各自的画质代价；
5. 明确说"不建议做"的条件。

不要给"可以做，用 HLS 就行"这类结论。
```

## P7 双版本修复（现场试错成本高时）

```text
请给两版修复：
- 保守版：只修根因，改动 ≤ 3 处，不动架构；
- 增强版：在保守版基础上做一项可量化优化。

每版都要写：改了哪些文件/行、为什么这一行能修、预期指标变化、回退方法。
两版分别出 bit，分别记录指标——用户要在现场二选一。
```

## P8 报告生成（交给陌生人也能复现）

```text
基于本次工作，写一份报告，结构固定：
1. 现象（可复现描述 + 图/日志位置）
2. 预算（时间/带宽/容量/量化四个数字，带算式）
3. 假设与判决（哪条成立、哪条被证伪、证据）
4. 改动（文件 + 行 + 因果链）
5. 验证（仿真判据原文、时序/资源数值、上板记录）
6. 失效条件（什么情况下这个结论不再成立）
7. 未解决项与风险

要求：每个结论后面标注可信度（高/中/低）；禁止出现"应该""基本""大概"。
```

## P9 让 AI 当反方（红队）

```text
你现在的角色是评审专家，不是助手。请攻击下面这个结论：

结论：<贴结论>
证据：<贴日志/数字>

请给出：
1. 三条"如果成立就推翻结论"的反例；
2. 结论里最脆弱的一环（数据来源？判据？假设？）；
3. 若要在 30 分钟内证伪它，最小实验是什么。

不要给改进建议，只做攻击。
```

**用途**：在写进报告前，先被自己人打一遍比被评委打一遍便宜。

## P10 把踩坑转成技能条目

```text
把下面这次失败，改写成一条可复用的技能条目：

失败经过：<发生了什么、当时怎么想的、怎么发现的>

格式：
- 触发条件（什么情况下会遇到）
- 现象（可观测的指纹）
- 根因（一句话，能写成算式或信号行为）
- 排查步骤（3 步内，能自动化最好）
- 对策（最小改动）
- 失效条件（什么时候这条经验不适用）
- 来源（哪次失败、哪个文件/行）

要求：不要写成"要注意 XX"这种无法执行的建议。
```

## 通用约束（贴在任何提示词后面都有效）

```text
附加约束：
- 没算出数字之前，不要给修改方案；
- 每条结论必须能被一个观测证伪，请写出那个观测；
- 区分"事实（测到的）"、"推断（算出来的）"、"猜测（没有依据的）"，并分别标注；
- 如果信息不足，先列缺失项，不要用假设填补。
```
